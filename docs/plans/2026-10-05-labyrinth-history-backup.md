# Labyrinth history backup in catbird-mls (feature `labyrinth`)

**What this is.** Labyrinth 1.1 is Meta's protocol for encrypted chat *history*. Catbird's implementation is the private `labyrinth` crate (`~/Developer/labyrinth`, bookmark `labyrinth-1.1`), and mls-ds serves it under `blue.catbird.labyrinth.*` (local bookmark `local/labyrinth-backend-20261004` in mls-ds). This change wires the crate into the shared Rust orchestrator behind a new cargo feature, `labyrinth`, which is off by default. A device can now back up the messages it sends, restore onto a new device with a recovery code, read or import a conversation's history, revoke another device, and re-archive before leaving. Nothing here is pushed, and platform bindings are not regenerated.

Code: `src/labyrinth/` (module docs list each file). Crate design: `docs/MLSDS_BACKEND.md` and `docs/DECISIONS.md` in the labyrinth repo. Server admission (headers, signature domain): mls-ds `server/src/labyrinth/auth.rs`.

## What is wired

| Hook | Where | Behaviour |
|---|---|---|
| Enable / reopen | `MLSOrchestrator::labyrinth_enable` | Opens the saved state, or creates the mailbox (`Labyrinth::initialize`). |
| Recovery code | `labyrinth_create_recovery_code` | Creates a bundle and returns the code. |
| Restore | `labyrinth_restore_with_recovery_code` | Enrolls this device from a code. |
| Archive on send | `send_payload_message` → `labyrinth_archive_sent` → `queue.rs` worker | Queues a durable row (local DB write only); a background worker flushes in batches (D7 amended). |
| Flush now | `labyrinth_flush_archive` | Drains the queue (call at suspend and launch). |
| Chat-device revocation | `remove_device` → `labyrinth_revoke_chat_device` | Revokes the Labyrinth device the removed chat device enrolled (D9 superseded). |
| Sign-out / account deletion | `labyrinth_sign_out`, `labyrinth_delete_account`, `perform_silent_recovery` | Erase saved state and queue; delete also runs server-side `deleteAccountData` and retracts PDS records (D5 gap closed). |
| PDS directory | `SessionDeps::pds` via `OrchestratorAPICallback::*_labyrinth_mailbox_keys` | `CompositeDirectory` over PDS + mls-ds when the platform implements it (D6 amended). |
| Space mailbox | `SessionDeps::space` via `OrchestratorAPICallback::submit_labyrinth_space_request` / `labyrinth_space_enabled` (`src/labyrinth/space.rs`) | A new mailbox goes into the account's own PDS Space when the platform reaches it and publishes `mailboxKeys`; the placement is saved per device (D11). |
| History | `labyrinth_load_history`, `labyrinth_import_history` | Decrypts history; import stores missing messages through `MLSStorageBackend`. |
| Revoke | `labyrinth_revoke_device(device_key_hex)` | Revokes a device and opens a new epoch ([CB-11]). |
| Leave | `leave_conversation` → `labyrinth_rearchive_before_leave` | Best effort ([CB-22]). |
| Shutdown / account switch | `clear_runtime_state` | Drops the in-memory session. The saved state is kept. |
| UniFFI | `src/labyrinth/ffi.rs` (child of `orchestrator_bridge`) | `labyrinth_enable_backup`, `labyrinth_create_recovery_code`, `labyrinth_restore_with_recovery_code`, `labyrinth_load_history_page`, `labyrinth_import_history`, `labyrinth_revoke_device`, `labyrinth_flush_archive`, `labyrinth_sign_out`, `labyrinth_delete_account` |

## 2026-10-05 · catbird-mls · D3 A separate gateway seam for Labyrinth requests
Chose: a feature-gated `MLSAPIClient::submit_labyrinth_request(LabyrinthRequest)` whose default refuses. `LabyrinthRequest` carries the NSID (the service-auth `lxm`), the path, the body and the two signed-write headers. The one non-Labyrinth query, `getConversationState`, uses the existing `submit_prepared_request`. Because: `PreparedRequest` has no header field and `CanonicalOperation` is a closed enum that is mirrored across UniFFI. Widening either would change the FFI for every caller. Rejected: adding Labyrinth variants to `CanonicalOperation`.
Consequence: the UniFFI `OrchestratorAPICallback` does not forward the new method yet, so on iOS and Android every Labyrinth call fails with `Api("this gateway does not implement Labyrinth requests")`. Next step: add the callback method, then run `ffi-propagate`.
**Amended 2026-10-05:** `OrchestratorAPICallback::submit_labyrinth_request(method, nsid, path, body, headers: [FFILabyrinthHeader])` now exists, with a refusing default, and `APIAdapter` forwards it. UniFFI cannot `#[cfg]` a callback method (the scaffolding fails to compile), so it, and the four PDS methods of D6, are in **every** build's FFI surface, not only `--features labyrinth`. Bindings are not regenerated. **Follow-up: run `ffi-propagate` (Swift + Kotlin + .so/.xcframework from one revision); checksums move even for builds that never call Labyrinth.**

## 2026-10-05 · catbird-mls · D4 Signing uses the chat device key through platform custody
Chose: sign through `CredentialStore::sign_clean_chat_transcript`, falling back to the MLS identity signer. This is the same path as signed clean-chat and direct-request bodies. The signature is verified locally before use. Labyrinth's `TransportSigner` cannot fail, so a failure produces a zero signature and is recorded in a latch, and the session then returns `Credential(..)`. Because: the private key must never cross the FFI. Every Labyrinth signing input carries its own `catbird.labyrinth.*` or `CATBIRD-LABYRINTH-WRITE\0` prefix, so these signatures cannot be confused with clean-chat signatures.
Override by: a fallible signer trait in the crate.

## 2026-10-05 · catbird-mls · D5 Client state lives in the encrypted MLS database
Chose: store `Labyrinth::export_state` in `MlsCryptoContext::compare_exchange_request_value`, namespace `labyrinthClientState`, keyed by account DID. This is the SQLCipher store that already holds direct-request keys. The write is a compare-and-swap, so a concurrent writer (for example the notification extension) is reported instead of being overwritten silently. Rejected: the `KeychainAccess` callback, which the orchestrator cannot reach (it is owned by `MLSContext`). ~~Gap: there is no delete API for request values, so disabling Labyrinth cannot erase the state yet.~~ [Edit 2026-10-05: closed. `MlsCryptoContext::delete_request_value` (default `OperationNotSupported`; `MLSContext` deletes the row) backs `StateVault::delete`. `labyrinth_sign_out` erases the state and archive queue; `labyrinth_delete_account` runs the crate's `purge_account` (server-side `deleteAccountData` over mls-ds, PDS retract) then erases both; `perform_silent_recovery` erases the state because the chat key it was bound to is gone. Platforms must call `labyrinth_sign_out` on sign-out/account removal: there is no orchestrator-level sign-out hook to attach it to.]

## 2026-10-05 · catbird-mls · D6 mls-ds is the only directory
Chose: `XrpcDirectory` (mls-ds) is the client's directory, with no PDS `mailboxKeys` publisher. Because: the crate has no atproto PDS store yet, so `CompositeDirectory` has nothing to cross-check against. Cost: with the mailbox in mls-ds, the [CB-28] truncation check and first contact under [CB-29] both rest on mls-ds alone (labyrinth design §1c). Override by: adding a PDS directory and publisher, then wrapping both in `CompositeDirectory` in `SessionDeps::backends`.
**Amended 2026-10-05:** done, behind a platform switch. The crate's `store::pds` (`PdsRecords`, `PdsDirectory`, `PdsPublisher`; `mailboxKeys/self` plus immutable `mailboxKeys/<12-digit epoch>`) is wired through new `OrchestratorAPICallback` methods: `labyrinth_pds_enabled`, `put_/get_/delete_labyrinth_mailbox_keys` (the platform or nest owns the PDS session and does `putRecord`/`getRecord`/`deleteRecord`). When `labyrinth_pds_enabled()` is true, `SessionDeps::pds` is set: every epoch is also published to the PDS, peers' heads are cross-checked PDS vs mls-ds (a disagreement is `DirectoryFork`), and opening a session backfills a missing or stale PDS record. When false, mls-ds stays the only directory as before. Rejected: always-on PDS, which would break every platform that has not implemented the callbacks.

## 2026-10-05 · catbird-mls · D7 Flush each sent message, archiving inline and best effort
Chose: archive and flush each sent message, awaited inside `send_message` after local storage. A failure is logged and never fails the send. Because: the state blob does not include unflushed batches, so a killed app would silently lose buffered history. Cost: one `appendBatch` per message, plus a `getConversationState` and roster lookups, all added to send latency. Rejected: buffering up to 256 messages per batch ([CB-20]), and detached background archiving, which suspension makes unreliable. Override by: flushing on a timer or at lifecycle suspend, or spawning the archive task.
**Amended 2026-10-05:** superseded by a background queue (`src/labyrinth/queue.rs`). The send hook only writes a durable `PendingArchive` row (request-value namespace `labyrinthArchiveQueue` in the SQLCipher DB) and wakes a per-account worker; no network call stays on the send path. The worker flushes at `max_batch` rows (default 32) or `max_delay` after the first (default 2 s), archives all pending rows grouped by conversation with one `flush` (one `appendBatch` per conversation and MEK), then removes them. Crash safety: rows are removed only after the write; rows left `inflight` by a crash between write and removal are looked up (`load_message`) and dropped if this account's copy exists, so nothing is archived twice; a failed flush drops the in-memory session so its outbox is not reused. Platforms should call `labyrinth_flush_archive` at suspend and launch. `labyrinth_set_archive_policy` tunes the triggers.

## 2026-10-05 · catbird-mls · D8 Roster and import rules
Chose:
- The roster is every participant in `getConversationState` that is `active` and has `leafCount > 0`. `labyrinthHead` is not required, because `resolve_roster` skips DIDs that are not enrolled.
- Import stores sender-mode messages only: owner copies carry no sender DID. It skips [CB-31] conflict copies and frames that are not an `MLSMessagePayload`.
- Imported messages get `epoch = 0` and `sequence_number = 0`, because they have no MLS coordinates.

Override by: editing `hooks::roster_members` or `labyrinth_import_history`.

## 2026-10-05 · catbird-mls · D9 Revoking a chat device does not revoke its Labyrinth device
Chose: revocation is explicit, through `labyrinth_revoke_device(device_key_hex)`. Because: at `labyrinth-1.1` a Labyrinth device record has no link to a chat device id. The `gaps` lane in the labyrinth repo (`8b634487`, unmerged) adds a `chatBinding` ([CB-36]). Once that lands, `remove_device` can map a chat device to its Labyrinth device and revoke both.
**Superseded 2026-10-05:** `remove_device` now revokes the chat device first (mls-ds requires that order), then calls `labyrinth_revoke_chat_device(chat key from listDevices.signaturePublicKey)`, which revokes every unrevoked Labyrinth device whose verified chat binding names that key (crate `Labyrinth::revoke_chat_device`) and opens a new epoch for each. Best effort: rotations already drop members whose chat device is not current, so a failure only delays the exclusion to the next rotation.

## 2026-10-05 · catbird-mls · D10 Second security review: the queue fails per conversation and never silently; deletion never strands the user
Context: the second Labyrinth security review found several problems. `flush_queue` was all-or-nothing, and one member whose epoch failed `resolve_roster` (`EpochRollback`, `Unattested`, `DirectoryFork`) aborted every archive. A peer who legitimately reset its mailbox stayed pinned-out forever. Reads carried no device signature. A failed remote deletion made account deletion fail. The crate half is in the labyrinth repo's `docs/DECISIONS.md` (2026-10-05, "Second security review, client half").

Chose (provisional):
- **Per-conversation flush** (`src/labyrinth/flush.rs`). Each conversation is resolved, archived and written on its own; one failing never holds back another.
  - Roster members that fail a trust check are excluded and recorded (`status.rs`, `excluded_members`, `needs_repin` for pin conflicts). They are never dropped silently. Transient errors still fail the conversation, so a network blip never excludes anyone.
  - A conversation mls-ds no longer has (`ConversationNotFound`) drops its rows, with the reason recorded.
  - Non-transient failures count per row. After `MAX_FAILURES` = 5 a row is quarantined: kept, skipped, and reported until `labyrinth_retry_quarantined`. Transient failures are no response, 5xx, 408 and 429; they are recorded but not counted, and the worker backs off.
  - The queue holds at most `MAX_QUEUE_ROWS` = 1000 rows per account. When full, the oldest quarantined row is evicted; if there is none, the new message is refused. Either way the drop is recorded.
- **Re-pin.** `labyrinth_propose_repin(did)` returns the old and new safety numbers. `labyrinth_repin_peer(did, head)` accepts exactly the head the user saw. Both go through the crate's `propose_repin` / `repin_peer`, which require the new genesis to be attested by a current chat device. A re-pin clears that peer's pin-conflict exclusions and retries quarantined rows.
- **Signed reads.** `GatewayXrpcTransport` adds `catbird-labyrinth-read` and `catbird-labyrinth-read-signature` to every Labyrinth query, signed by the chat device key over every wire parameter (including `actorDeviceId`). If the signer fails, nothing is sent. The format is byte-identical to mls-ds; both repos pin the golden vector `labyrinth-wire/tests/vectors/labyrinth_read_header.json`.
- **Account deletion.** `labyrinth_delete_account` always erases this device's state and queue, even if the session cannot be opened (offline).
  - A remote failure is recorded as `pending_remote_deletion`. It is retried by a background task (2 s doubling to 10 min), at `labyrinth_flush_archive` (call it at launch), and on demand (`labyrinth_retry_remote_deletion`).
  - `labyrinth_enable` refuses while a deletion is pending, because the retry would erase the new mailbox.
- **Status API** (UniFFI): `labyrinth_archive_status`, `labyrinth_retry_quarantined`, `labyrinth_clear_archive_reports`, `labyrinth_propose_repin`, `labyrinth_repin_peer`, `labyrinth_retry_remote_deletion`, and `labyrinth_list_threads`, which returns `incomplete_sequencers` when the list is partial.
  - History pages now carry `redacted` with a label: `Unsent`, `AccountDeleted` (only when the sequencer DS signature verifies) or `RemovedByServer`.
  - `labyrinth_delete_account` now returns a record with `remote_pending`. Bindings are not regenerated; run `ffi-propagate`.
  - Known gap: there is no source for the mls-ds redaction key yet, so over mls-ds alone account deletions show as `RemovedByServer` (fail closed).

Reversible until: any push of catbird-mls. Override by: editing `flush.rs`, `status.rs` and `hooks_status.rs`. Behaviour is pinned by `src/labyrinth/review_tests.rs`.

## 2026-10-11 · catbird-mls · D11 New mailboxes go into the account's PDS Space when the platform reaches it
Chose:
- **Transport.** `OrchestratorAPICallback` gains `labyrinth_space_enabled()` and `submit_labyrinth_space_request(method, nsid, path, body)` (refusing defaults; `MLSAPIClient` counterparts behind the feature). The platform sends `com.atproto.space.*` to the account's own PDS with its OAuth session, like `com.atproto.repo.*`, with no service auth. `SpaceXrpcTransport` refuses any other NSID. The crate's `SpaceMailboxStore` (labyrinth feature `space`) does the rest, against `at://{did}/space/blue.catbird.labyrinth.mailbox/self`, and never calls `createSpace`.
- **What moves.** Only the mailbox: devices, epochs, members, recovery bundles, owner archive. `mailboxKeys` goes to the public repo through the PDS publisher. Threads, MEKs, the ORF, attachment references, chat device keys and the head chain stay on mls-ds, which becomes the independent directory for [CB-28] (labyrinth `docs/MLSDS_BACKEND.md` §1c).
- **When.** Space needs both `labyrinth_space_enabled` and `labyrinth_pds_enabled`. A device without saved state probes once: an existing Space mailbox wins, then an existing mls-ds mailbox, else a new one goes into the Space. The answer is saved in request-value namespace `labyrinthMailboxPlacement` next to the client state, erased with it (sign-out, account deletion, silent recovery). Saved state without a placement predates this and is mls-ds. Nothing moves a mailbox between backends; an account whose mailbox is in a Space fails clearly on a platform that cannot reach it. That includes a new device there: the probe sees a head on mls-ds (or `mailboxKeys` on the PDS) with no mls-ds mailbox and refuses, instead of opening a second mailbox on mls-ds (which would also stop the Space devices' head publishes).
- **Deletion.** `SpaceMailbox` wraps the Space store so `deleteAccountData` still runs on mls-ds (atomic cross-DS redaction, ORF, head chain), followed by a purge of every Space record and the `mailboxKeys`. `SessionDeps::delete_account_remote` (the retry with no saved state) does mls-ds first and then purges the Space whenever the platform reaches it, whatever the placement was.
- **Feature.** The `labyrinth` dependency now enables the crate's `space` feature (it implies `xrpc`).

**Server rule.** mls-ds on `labyrinth-backend-20261004` does not accept a Space account. `publishEpochHead` only re-publishes epochs already in its own `labyrinth.epochs` (`server/src/labyrinth/repo/directory.rs:139`). `deleteOrfState`, `purgeMailbox` and `deleteAccountData` need a Labyrinth device bound on mls-ds (`require_bound`). With the mailbox in a Space, the head publish after every epoch fails with `EpochNotFound`, revocation cannot drop the revoked device's ORF state, and account deletion cannot reach mls-ds. Josh chose (2026-10-11) to let mls-ds accept such accounts: joshlacal/mls-ds#55 (draft, into `labyrinth-backend-20261004`). For a DID with no `labyrinth.mailboxes` row, it records heads directly under the chain and caller-attestation checks, and those three calls need no bound device. The crate's memory reference server now applies the same rules (joshlacal/labyrinth#4), so the tests here fail wherever mls-ds would. Until mls-ds#55 is deployed, platforms must keep `labyrinth_space_enabled` false.
Reversible until: a platform reports `labyrinth_space_enabled`. Override by: editing `src/labyrinth/space.rs` and `SessionDeps::probe_placement`. Tests: `src/labyrinth/space_tests.rs` against the reference servers, and `src/labyrinth/live_space_tests.rs` against a real `permissioned-data` PDS (opt-in, below).

## Tests

Gap-closure lane (2026-10-05) adds, in `src/labyrinth/queue_tests.rs` and `ffi.rs`: one flush → one `appendBatch` for many queued messages; a crash after the write does not archive twice; a crash before the write archives on retry; PDS publication, backfill and the fork refusal; chat-device revocation; sign-out and account deletion erase the vault; the orchestrator worker flushes by size and by time and nothing is written on the send path; `APIAdapter` forwards the Labyrinth and PDS callback methods.


`src/labyrinth/tests.rs` covers the following:
- A mock gateway checks every request the way mls-ds admission does, then serves it from the crate's memory-backed reference server. It checks `actorDeviceId`, the base64url write body under `deny_unknown_fields`, the lowercase-hex digest and operation id, the NSID, the 300-second clock window, and the Ed25519 signature over the domain and body.
- The full lifecycle: archive, a recovery-code restore on a second device, history, revocation, reopening from the vault, and sending after rotation.
- Re-archive, a forged-key write, a signer failure, a concurrent state writer and the roster filter.
- One orchestrator test on the e2e harness (`TestWorld`). A send is archived, a second device of the account restores and imports the message into its own storage, leaving re-archives, and the second device revokes the first.

`src/labyrinth/live_space_tests.rs` runs the orchestrator session against a real PDS from the upstream `permissioned-data` branch, started by the labyrinth repo's `scripts/space-pds/start.mjs`. It is opt-in through `LABYRINTH_SPACE_PDS` and passes trivially without it. It covers: Alice's first device creating her mailbox in her Space, Bob (on mls-ds) archiving to her through the PDS × mls-ds composite, a recovery-code restore from the Space, a revocation that opens epoch 1 there and moves the mls-ds head chain, and account deletion emptying the Space and her `mailboxKeys`. mls-ds is the reference server here.

No harness runs catbird-mls against a live mls-ds. The mls-ds lane's `e2e-tests` crate depends on `../../catbird-mls` and could host such a test once the gateway seam is implemented for its HTTP client.
